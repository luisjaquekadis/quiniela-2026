Arquitectura General

Quiniela Mundial 2026 - Architecture One-Pager

La Quiniela Mundial 2026 es una aplicación web progresiva (PWA) de alto rendimiento, diseñada para competencias de pronósticos deportivos en tiempo real. Su arquitectura está orientada a la velocidad extrema, bajo costo operativo (Serverless) y resiliencia offline.

1. Stack Tecnológico

[!TIP] La aplicación evita intencionalmente frameworks pesados (como React o Angular) para garantizar tiempos de carga sub-segundo, incluso en redes móviles lentas.

  • Frontend: Vanilla JavaScript (ES6+), HTML5, y CSS3 (Diseño Neo-Brutalista Oscuro).
  • Backend / Sincronización: Firebase Firestore (BaaS).
  • Live Scores: Python Scripts (Extracción ESPN) + JSON estático.
  • Hosting: Netlify (CDN Global).

2. Arquitectura de Datos: "Local-First" + Reactividad

El núcleo del sistema es la clase QuinielaStorage (profiles.js), que actúa como un puente inteligente entre la interfaz y la nube. 

graph TD
    UI[Interfaz de Usuario / DOM] --> |Lee y Escribe instantáneamente| LS[(LocalStorage)]
    LS --> |Dispara| Sync[Capa de Sincronización]
    Sync --> |Push: Guarda cambios| FB[(Firebase Firestore)]
    FB --> |Pull: onSnapshot Listeners| Sync
    Sync --> |Actualiza si hay diferencias| LS
  1. Velocidad Local: Todas las acciones del usuario (guardar pronósticos, calcular puntos) leen y escriben primero en el localStorage del navegador. Esto asegura que la interfaz nunca se quede "pensando".
  2. Listeners Reactivos: En segundo plano, conexiones silenciosas de Firebase (onSnapshot) escuchan cambios realizados por otros usuarios. Si alguien más hace un cambio, Firebase envía una notificación al cliente, se actualiza la caché local y la UI se repinta al instante.

3. Modelo Multigrupo (Multi-tenant)

La base de datos en Firestore está estructurada jerárquicamente para soportar múltiples "salas" o "grupos" privados de forma aislada.

Firestore Root
└── groups/
    ├── default/
    │   ├── profiles/ {Jaque: {...}, Kimi: {...}}
    │   ├── predictions/ {Jaque: {...}, Kimi: {...}}
    │   └── misc/
    ├── mango_fc/
    │   ├── profiles/ ...
    │   └── predictions/ ...

Cuando un usuario hace login indicando un ID de grupo, la aplicación purga su caché local y se suscribe únicamente a la rama de Firestore correspondiente a ese grupo.

4. Ingesta de Marcadores en Vivo (ESPN)

Para evitar reventar las cuotas de lectura de Firebase (Firebase Quotas) preguntando por resultados en vivo cada segundo, la aplicación utiliza una arquitectura híbrida de bajo costo:

  1. El Motor Python: Un script (sync_api_espn.py) consulta la API pública de ESPN y compila el calendario oficial y los goles en un archivo estático hiper-ligero: api/2026.json.
  2. Polling Estático: El cliente (navegador) hace peticiones cada 30 segundos a este archivo JSON estático alojado en Netlify.
  3. Escritura Unidireccional: Si el cliente detecta un resultado nuevo en el JSON, lo sube a Firebase (updateCloudKey) para que todos los usuarios del grupo recalculen sus puntos automáticamente.

[!IMPORTANT] Gestión de Puntos: La función recalculateAllPoints() recalcula los puntajes de todos los usuarios del grupo desde cero cada vez que se detecta un cambio en un marcador oficial o un nuevo pronóstico. Esto garantiza que nadie se desincronice jamás de la tabla general.

Resumen de la Migración a onSnapshot

Resumen de Cambios: Optimización de Firebase

He completado exitosamente la migración del sistema de consultas de Firebase para proteger tu cuota de lecturas.

¿Qué cambió?

[!TIP] De "Preguntar" a "Escuchar" Anteriormente, cada usuario de la aplicación "golpeaba" la puerta de Firebase cada 8 segundos para ver si había cambios (setInterval). Si tenías 10 usuarios conectados por 1 hora, eso generaba 4,500 solicitudes a la base de datos (incluso si nadie había modificado nada).

Ahora, la aplicación usa onSnapshot. Esto significa que Firebase mantiene un canal silencioso abierto y solo envía datos cuando alguien realmente guarda un pronóstico o cambia un marcador. Esto reduce el consumo de cuota en un ~99% cuando la app está inactiva.

Archivos Modificados

  • profiles.js: Se agregó el método listenToCloudChanges() que crea conexiones inteligentes a las colecciones de profiles, predictions y matches.
  • app.js: Se eliminó el "polling" agresivo de 8 segundos y se conectó la interfaz visual a los nuevos "listeners" de Firebase. Además, se implementó un chequeo ligero y separado cada 30 segundos exclusivamente para buscar actualizaciones oficiales de ESPN (sin gastar cuota de Firebase).

Tareas Ejecutadas

Tareas Post-Recuperación de Firebase

A continuación se detallan las tareas que deben realizarse y verificarse una vez que Firebase levante la restricción de "Quota Exceeded" (Límite de cuota excedido).

  • [x] Verificar la Sincronización Inicial (No Bloqueante)
  • Comprobar que la aplicación descarga correctamente los perfiles y predicciones desde la nube al cargar la página.

  • Asegurarse de que el enfoque no bloqueante que implementamos sigue permitiendo una carga rápida de la interfaz visual antes de que lleguen los datos.

  • [x] Sincronización de Nuevos Perfiles Locales

  • Si los usuarios crearon cuentas o hicieron predicciones mientras Firebase estaba caído (guardado en localStorage), verificar que el sistema "auto-sane" la nube subiendo esos perfiles faltantes sin sobrescribir los datos de otros.

  • [x] Verificar Sincronización de Pronósticos (Predicciones)

  • Validar que al guardar un pronóstico, la petición a Firebase Firestore se complete exitosamente.

  • Confirmar que los cambios realizados en un dispositivo (ej. teléfono) se reflejen automáticamente en otro dispositivo (ej. computadora) gracias al polling en segundo plano.

  • [x] Probar la Funcionalidad de Grupos (joinGroup)

  • Iniciar sesión utilizando un ID de grupo específico (ej. mango_fc).

  • Verificar que el sistema limpia correctamente el almacenamiento local y descarga exclusivamente los datos de ese grupo desde Firebase sin quedarse colgado en "Conectando al Grupo...".

  • [x] Optimizar el Polling en Segundo Plano

  • Actualmente, la aplicación hace "polling" (pregunta a Firebase por cambios) cada 8 segundos (setInterval en app.js).

  • Tarea: Evaluar si esta frecuencia es la causante principal del exceso de cuota. Considerar cambiar este mecanismo por Snapshot Listeners nativos de Firebase (onSnapshot), los cuales son mucho más eficientes en consumo de cuota porque solo consumen lecturas cuando hay un cambio real en la base de datos.

  • [x] Validar Integración de Marcadores ESPN en la Nube

  • Verificar que la función syncOfficialResults() logre actualizar el documento central de matches en Firebase con los resultados en vivo de ESPN.
  • Asegurarse de que esta subida no pise de forma destructiva las estructuras base del JSON.
